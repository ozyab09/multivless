# 1. Описание проекта

## 1.1. Назначение

Multi-Exit VLESS Gateway — сервис для Linux, предназначенный для одновременного использования нескольких VLESS-серверов в качестве независимых исходящих точек подключения с интеллектуальным распределением пользовательских соединений между ними.

Основная задача проекта — увеличить суммарную пропускную способность при одновременной работе нескольких клиентских приложений и сетевых соединений за счёт использования нескольких VLESS-серверов.

В отличие от обычного VLESS-клиента, который использует один выбранный сервер или переключается между серверами, Multi-Exit VLESS Gateway должен поддерживать одновременную работу всех доступных серверов и самостоятельно распределять между ними новые подключения.

Система должна работать как самостоятельный сетевой сервис на Ubuntu и предоставлять единую точку подключения через SOCKS5.

## 1.2. Основные возможности

Сервис должен обеспечивать:

1. Одновременную работу с несколькими VLESS-серверами.
2. Импорт серверов из нескольких VLESS-подписок.
3. Ручное добавление VLESS-ссылок.
4. Импорт конфигурационных файлов.
5. Автоматическое обновление подписок.
6. Постоянный мониторинг доступности серверов.
7. Измерение задержки и качества соединений.
8. Интеллектуальную балансировку новых подключений.
9. Независимый выбор VLESS-сервера для каждого нового SOCKS5-соединения.
10. Автоматическое исключение неработающих серверов.
11. Автоматическое возвращение восстановившихся серверов в пул балансировки.
12. SOCKS5 с авторизацией.
13. Поддержку нескольких пользователей SOCKS5.
14. Web-интерфейс управления.
15. REST API.
16. CLI.
17. Статистику по серверам и подключениям.
18. Автоматический запуск через systemd.
19. Установку через DEB-пакет.
20. Установку через install.sh из GitHub.
21. Запуск через Docker и Docker Compose.
22. Возможность последующего расширения до агрегации пропускной способности нескольких каналов для одного соединения.

## 1.3. Основной архитектурный принцип

**Не реализовывать протокол VLESS самостоятельно.**

Для работы с VLESS использовать готовый транспортный движок sing-box.

Собственное приложение отвечает за управление, мониторинг, балансировку, конфигурацию, статистику и пользовательский интерфейс.

sing-box отвечает за непосредственную обработку сетевого трафика, установление VLESS-соединений и работу транспортных протоколов.

## 3.2. Логические компоненты

Система должна состоять из следующих компонентов.

Отвечает за:

- Приём пользовательских TCP-подключений.
- Обработку SOCKS5-протокола.
- Аутентификацию пользователей.
- Проверку ограничений пользователя.
- Передачу информации о новом соединении в Connection Router.
- Установление соединения через выбранный outbound.
- Учёт переданных данных.
- Завершение соединений.
- Обработку ошибок.

### 3.2.2. Connection Router

Центральный компонент маршрутизации.

Отвечает за:

- Получение информации о новом соединении.
- Получение списка доступных outbound.

- Закрепление outbound за установленным соединением.
- Обеспечение независимого выбора для каждого нового соединения.

Каждое новое SOCKS5 TCP CONNECT должно рассматриваться как отдельная единица балансировки.

Выбранный outbound не должен меняться в процессе существующего соединения.

Отвечает за оценку качества серверов и выбор наиболее подходящего.

# 5. Требования к балансировке

## 5.1. Общая логика

Основной режим работы — балансировка каждого нового TCP-соединения.

Пример:

```text
Client A
  |
  +-- Connection 1 --> VLESS Server 1
  |
  +-- Connection 2 --> VLESS Server 2
  |
  +-- Connection 3 --> VLESS Server 3

Client B
  |
  +-- Connection 4 --> VLESS Server 2
  |
  +-- Connection 5 --> VLESS Server 1

Client C
  |
  +-- Connection 6 --> VLESS Server 3
````

Один пользователь SOCKS5 может одновременно использовать несколько VLESS-серверов.

Разные соединения одного пользователя не обязаны использовать один и тот же исходящий IP.

## 5.2. Алгоритмы

Обязательно реализовать:

### Round Robin

Последовательный выбор доступного сервера.

Применяется как fallback и для тестирования.

### Random

Случайный выбор сервера.

### Least Latency

Выбор сервера с минимальным RTT.

### Least Connections

Выбор сервера с наименьшим количеством активных подключений.

### Weighted

Выбор с учётом пользовательских весов.

### Adaptive

Основной алгоритм.

Учитывает:

- Задержку.
- Активные подключения.
- Оценочную пропускную способность.
- Стабильность.
- Ошибки.
- Пользовательский вес.

## 5.3. Adaptive Score

Для начальной реализации использовать следующую формулу:

```
Score =
    Latency       * 0.30 +
    Connections   * 0.25 +
    Throughput    * 0.35 +
    Reliability   * 0.10
```

Все составляющие нормализуются в диапазон 0–100.

Чем меньше итоговый Score, тем предпочтительнее сервер.

Весовые коэффициенты должны быть настраиваемыми.

При изменении весов их сумма должна нормализоваться до 1.0.

### 5.3.1. Latency

Оценка RTT.

Предпочтение отдаётся серверам с меньшей задержкой.

Для расчёта использовать сглаженное значение, а не только последний результат проверки.

### 5.3.2. Connections

Оценка количества активных подключений.

Необходимо учитывать относительную загрузку сервера, а не только абсолютное количество соединений.

При наличии ограничения `max_connections` использовать долю от установленного лимита.

### 5.3.3. Throughput

Оценка доступной пропускной способности.

Учитывать:

- Текущую скорость.
- Историческую скорость.
- Успешность передачи данных.
- Результаты ограниченных тестов пропускной способности.

Не выполнять постоянные тяжёлые speedtest-запросы ко всем серверам.

### 5.3.4. Reliability

Оценка надёжности.

Учитывать:

- Процент успешных проверок.
- Ошибки подключения.
- Время последнего успешного соединения.
- Частоту переходов между ONLINE и OFFLINE.

## 5.4. Начальное состояние

Для нового сервера, у которого нет статистики:

1. Выполнить первичную проверку.
2. При успешной проверке включить сервер в пул.
3. Использовать нейтральную оценку производительности.
4. Собрать дополнительные метрики.
5. Постепенно адаптировать Score.

Необходимо избегать ситуации, когда новые серверы навсегда исключаются из балансировки из-за отсутствия исторических данных.

## 5.5. Сглаживание

Для предотвращения частых переключений предпочтительного сервера использовать:

- Exponential Moving Average.
- Минимальное время нахождения в статусе.
- Гистерезис.
- Ограничение изменения оценки за один цикл.

Настройки должны быть доступны через конфигурацию.

## 5.6. Закрепление соединений

После выбора outbound он закрепляется за конкретным соединением до его завершения.

Необходимо учитывать:

- HTTP keep-alive.
- HTTP/2.
- Долгоживущие TCP-соединения.
- WebSocket.
- TLS-соединения.
- Загрузки больших файлов.

Переключение существующего соединения между VLESS-серверами не требуется.

Sticky sessions по пользователю или домену не являются обязательными в MVP.

# 6. Управление VLESS-серверами

## 6.1. Источники

Поддерживать:

1. HTTP/HTTPS-подписки.
2. VLESS URI.
3. TXT-файлы.
4. JSON-конфигурации sing-box.
5. Несколько источников одновременно.

## 6.2. Форматы

Поддерживать распространённые варианты:

```
vless://UUID@HOST:PORT?PARAMETERS#NAME
```

В том числе параметры:

- encryption.
- security.
- sni.
- fp.
- pbk.
- sid.
- type.
- host.
- path.
- serviceName.
- flow.
- packetEncoding.
- fragment.

Набор поддерживаемых параметров определяется совместимостью с используемой версией sing-box.

Парсер должен:

- Проверять URI.
- Проверять обязательные параметры.
- Проверять допустимость портов.
- Проверять UUID.
- Корректно обрабатывать URL encoding.
- Корректно обрабатывать Base64.
- Возвращать понятные ошибки.
- Не завершать обработку всей подписки из-за одной некорректной записи.

## 6.3. Идентификация

Каждый сервер получает внутренний UUID/ID.

При повторном импорте:

- Сохранять ID известных серверов.
- Обновлять изменившиеся параметры.
- Не создавать дубликаты.
- Сохранять пользовательские настройки.
- Сохранять статистику.

Идентификатор не должен содержать секретные параметры подключения.

## 6.4. Обновление подписок

Для каждой подписки задаются:

- Название.
- URL.
- Интервал.
- Таймаут.
- Статус.
- Последнее обновление.
- Последняя успешная загрузка.
- Количество серверов.

Интервал по умолчанию — 6 часов.

Значение должно настраиваться независимо для каждой подписки.

Требования:

- Ручное обновление.
- Автоматическое обновление.
- Повторные попытки.
- Обработка HTTP-ошибок.
- Поддержка Last-Modified и ETag.
- Контроль размера ответа.
- Обработка редиректов.
- Проверка формата.
- Атомарное применение результатов.

Если подписка недоступна или содержит некорректные данные, использовать последнюю корректную версию.

Удаление старых серверов выполнять только после успешного обновления и проверки нового набора.

# 7. Health Check

## 7.1. Настройки по умолчанию

| Параметр              | Значение               |
| --------------------- | ---------------------- |
| Интервал              | 20 секунд              |
| Таймаут               | 5 секунд               |
| Ошибки до OFFLINE     | 3                      |
| Успехи до ONLINE      | 2                      |
| Параллельные проверки | 20                     |
| Первичная проверка    | Сразу после добавления |

## 7.2. Проверка доступности

Проверка должна осуществляться через конкретный VLESS outbound.

Необходимо проверить:

1. Возможность установить транспортное соединение.
2. Успешное установление VLESS-сессии.
3. Возможность отправить HTTP-запрос через туннель.
4. Получение ожидаемого ответа.
5. Время ответа.

Рекомендуемый endpoint:

```
https://www.gstatic.com/generate_204
```

URL должен быть настраиваемым.

Поддерживать резервные endpoint.

Проверки не должны использовать прямое подключение в обход VLESS.

## 7.3. Статусы

| Статус   | Описание                        |
| -------- | ------------------------------- |
| UNKNOWN  | Не проверен                     |
| ONLINE   | Работает                        |
| DEGRADED | Работает с ухудшением качества  |
| OFFLINE  | Недоступен                      |
| DISABLED | Отключён вручную                |
| ERROR    | Ошибка конфигурации или запуска |

## 7.4. Восстановление

После достижения порога ошибок:

- Сервер исключается из новых выборов.
- Продолжаются периодические проверки.
- Сохраняется история отказа.
- После двух успешных проверок сервер возвращается в пул.

При этом не требуется автоматически завершать уже установленные соединения.

# 8. SOCKS5 Gateway

## 8.1. Основные требования

Поддерживать:

- SOCKS5 TCP CONNECT.
- IPv4.
- IPv6.
- Domain name.
- Username/Password.
- Режим без авторизации.
- Несколько пользователей.
- Настраиваемый IP.
- Настраиваемый порт.

UDP ASSOCIATE в первой версии не реализовывать.

## 8.2. Конфигурация

Примеры:

```
socks5:
  enabled: true

  listen: 127.0.0.1
  port: 1080

  authentication: true
  allow_no_auth: false

- Bytes sent.

## 8.4. Fail-closed

Если нет доступных VLESS outbound:

- Новые соединения отклоняются.
- SOCKS5 возвращает соответствующую ошибку.
- Прямой выход в интернет запрещён.
- Проверки продолжаются.
- При восстановлении сервера работа возобновляется.

Нельзя использовать `direct` в качестве автоматического fallback.

# 15. Безопасность

## 15.1. SOCKS5

- По умолчанию слушать 127.0.0.1.
- Внешнее прослушивание разрешать только явно.
- При внешнем доступе требовать авторизацию.
- Ограничивать количество соединений.
- Защищать от перебора паролей.
- Не допускать несанкционированного использования прокси.

## 15.2. Web и API

- Административная авторизация обязательна.
- Пароли хранить через Argon2id.
- Использовать Bearer Token для API.
- Ограничивать частоту запросов.
- Защищать Web от CSRF и XSS.
- Вести аудит административных операций.
- Ограничивать доступ по IP.
- Не передавать секреты через URL.

## 15.3. VLESS-секреты

- Не выводить полные URI в логи.
- Не отображать UUID без необходимости.
- Не возвращать секреты через API.
- Шифровать секреты в хранилище.
- Ограничивать права доступа.
- Не включать секреты в диагностические архивы.

## 15.4. DNS

Обеспечить:

- DNS resolution через настроенный proxy-механизм.
- Отсутствие прямого DNS fallback.
- Настраиваемый DNS.
- Поддержку IPv4 и IPv6.
- Кеширование.
- Защиту от DNS leak для трафика, проходящего через SOCKS5.

Важно: первая версия не обеспечивает автоматическую защиту трафика процессов Ubuntu, которые не используют SOCKS5.

## 15.5. SSRF

Поскольку сервис загружает подписки и выполняет проверки:

- Запрещать доступ к loopback и внутренним административным адресам при загрузке подписок.
- Контролировать DNS resolution.
- Проверять адреса после редиректов.
- Ограничивать схемы URL.
- Ограничивать размер ответов.
- Ограничивать количество редиректов.
- Не выполнять команды из импортируемых конфигураций.

| Показатель                             | Требование                    |

- Перезапуск не повреждает SQLite.
- Конфигурация сохраняется после перезагрузки.
- Существующие соединения не переключаются произвольно.
- Ошибки должны иметь диагностические сообщения.
- Предусмотреть резервное копирование данных.

# 18. Агрегация каналов в будущем

Данная функциональность не входит в MVP.

Архитектура должна позволять её добавить без полной переработки приложения.

## 18.1. Цель

Использовать несколько VLESS-каналов одновременно для передачи данных одного соединения.

В отличие от обычной балансировки соединений, требуется разделение одного потока данных на сегменты, передача по нескольким каналам и восстановление исходного порядка на удалённой стороне.

## 18.2. Возможные технологии

- Multipath TCP.
- Специальный UDP-транспорт.
- QUIC с несколькими путями при наличии подходящей реализации.
- Собственный механизм агрегации.

## 18.3. Требования к архитектуре MVP

Предусмотреть интерфейсы:

```
type TransportProvider interface {
    Start() error
    Stop() error
    Health() HealthStatus
}

type ConnectionRouter interface {
    SelectOutbound(request ConnectionRequest) (string, error)
}

type Outbound interface {
    ID() string
    Status() ServerStatus
}

# 24. Главный принцип проекта

Multi-Exit VLESS Gateway должен быть не просто менеджером VLESS-подписок и не обычным прокси с переключением серверов.

Это самостоятельный интеллектуальный многосерверный прокси-шлюз.

Основная ценность продукта заключается в следующем:

**Все доступные VLESS-серверы работают одновременно, а каждое новое пользовательское соединение автоматически направляется через наиболее подходящий сервер с учётом его текущего состояния и производительности.**

Система должна самостоятельно обнаруживать отказ серверов, исключать их из балансировки, восстанавливать их после возвращения доступности и обеспечивать стабильную работу SOCKS5 без прямого выхода в интернет в обход прокси.

Архитектура должна быть расширяемой и позволять в последующих версиях реализовать полноценную агрегацию пропускной способности нескольких выходных каналов для одного пользовательского соединения.

**Приоритет разработки: корректная балансировка, отказоустойчивость, безопасность и производительность. Web-интерфейс и дополнительные функции не должны усложнять или ухудшать работу основного сетевого механизма.**
